# W5100S integration notes

Reviewed on 2026-10-27 from the [WIZnet W5100S documentation](https://docs.wiznet.io/Product/Chip/Ethernet/W5100S).
Document revisions and checksums are recorded in [References](REFERENCES.md#wiznet-documentation-baseline).
These notes translate the vendor material into Net4MSX requirements. They do not
select the host architecture or qualify the user's module. Requirements and
verification tasks below are project decisions; linked sources describe the chip.

## Chip capabilities and project scope

The controller combines a 10/100 Ethernet MAC/PHY with IPv4 protocol offload and
four hardware sockets. SPI modes 0/3 and an eight-bit parallel interface are
available. IP fragmentation and an ARP-cache table are absent; Auto-MDIX depends
on auto-negotiation. These are chip capabilities, not a guarantee of MSX transfer
speed or UNAPI coverage. [Source: product overview](https://docs.wiznet.io/Product/Chip/Ethernet/W5100S#features).

For Net4MSX, retain one socket allocator shared by applications and internal
services. DNS/DHCP, configuration and UNAPI error/state translation remain
software responsibilities. An Ethernet link alone cannot satisfy the networking
milestone. Raw IP, raw Ethernet, PPPoE, Wake-on-LAN and power saving do not enter
the initial scope merely because WIZnet documents them.

## Host access and hardware review

The W5100S parallel interface uses indirect addressing; unlike W5100, it has no
full direct-address bus. `MR.IND` and `MR.AI` are fixed at one. Thus consecutive
data accesses advance the indirect address. The existing four-offset interface
in [Hardware](HARDWARE.md#w5100s-interface) remains the candidate; serialize each
address/data sequence. W5100 compatibility claims do not justify copying its
electrical design or every register assumption.
[Source: comparison sheet, host interface and register changes](https://docs.wiznet.io/img/products/w5100s/application/w5100svsw5100_cs_v110e.pdf).

Selected datasheet facts for bring-up:

| Item | Baseline |
| --- | --- |
| Chip straps | `MOD[3:0]=0000` selects SPI; `010X` selects parallel |
| Buffer allocation | Separate 8 KiB TX and 8 KiB RX pools; reset gives each socket 2 KiB in each direction |
| Identification | `VERR` at `0080h` reads `51h` |
| Reset | Pin description requires `/RST` low longer than 560 ns and states 60.3 ms initialization |
| SPI timing | 70 MHz is theoretical; the timing note reports 33.3 MHz with a measured stable waveform |

Use sections 1.1, 2, 3.1.44 and 7.4 of the
[datasheet v1.2.8](https://docs.wiznet.io/img/products/w5100s/w5100s-ds-v128e.pdf).
Verify reset/settling and bus timing on the actual assembly. Its single `MODE`
header must be traced to the chip straps before accepting either interface.

The overview advertises 5 V I/O tolerance, but datasheet section 7.1 lists a
4.6 V maximum input voltage. Resolve this discrepancy with WIZnet before approving
an unshifted MSX connection. Module supply/regulator wiring and Pico translation
still require their own review.

## SPI read erratum

Erratum 1 describes invalid data during multi-byte SPI reads. Let `Tsys` be the
W5100S system-clock period, not the host SPI-clock period:

| Requirement | Minimum | At 100 MHz SYS_CLK | At 25 MHz SYS_CLK |
| --- | --- | --- | --- |
| First data ready, `TFDR` | `6 × Tsys + 30 ns` | 90 ns | 270 ns |
| Subsequent data ready, `TDR` | `3 × Tsys` | 30 ns | 120 ns |

The numerical columns are calculated from the vendor formulas. The errata
recommends an additional inter-byte delay of at least `3 × Tsys`; the first-byte
requirement also applies. [Source: errata v1.0.0, erratum 1](https://docs.wiznet.io/img/products/w5100s/w5100s-errata-en-v100.pdf).

For the Pico feasibility study, select a conservative clock and verify the
actual waveform, including burst/DMA paths. Exercise single-byte and burst reads
with changing patterns and record clock, delay implementation and error counts.
Any later system-clock change requires a timing review. Do not turn the headline
SPI rate into a cartridge throughput promise.

## TCP, UDP and interrupt handling

For TCP, check socket state after opening/connecting, and separate command
acceptance from send completion. RX handling must account for ring wrap, advance
`Sn_RX_RD` and issue `RECV`; TX handling must respect available space, update
`Sn_TX_WR` and observe completion or timeout before another send. Use received
size as well as event flags when deciding whether work remains.
[Source: TCP function note](https://docs.wiznet.io/Product/Chip/Ethernet/W5100S/Application-Note/tcp).

For Net4MSX, turn these flows into bounded progress steps. Test partial reads,
ring boundaries, remote closure and exhausted buffers through the public UNAPI
calls, including recovery after a failed command.

UDP RX records contain an eight-byte prefix: four bytes of source IP, two of
source port and two of payload length. Consume the prefix and the complete
datagram when releasing RX storage. Buffer capacity and datagram boundaries must
remain distinct from the caller's destination-buffer size. Sending can fail during
ARP resolution; check completion and timeout.
[Source: UDP function note](https://docs.wiznet.io/Product/Chip/Ethernet/W5100S/Application-Note/udp).

For Net4MSX, validate lengths before copying and implement UNAPI's truncation
semantics without exposing the hardware prefix. Exercise zero-length datagrams,
header/payload wrap and a subsequent datagram after truncation.

WIZnet recommends keeping interrupt handlers short and protecting SPI frames
against interrupt/task re-entry. Its interrupt masks and status handling need
explicit initialization.
[Source: interrupt application note, sections 1–3](https://docs.wiznet.io/img/products/w5100s/application/w5100s_an_interrupt_v100e.pdf).
For Net4MSX, start with polled progress; if interrupts are added, use them to
schedule work and preserve event state before acknowledging it. A Pico interrupt
input does not establish electrical compatibility with the MSX `/INT` line.

## Socket-less commands and library candidates

ARP/PING requests use a separate command path without opening a hardware socket.
Set peer/retry information, start the command, then observe success or timeout
before issuing another. PING also uses identifier and sequence registers.
[Source: SOCKET-less command application note](https://docs.wiznet.io/img/products/w5100s/application/w5100s_an_slc_v100e.pdf).
Net4MSX must serialize this engine separately. Keep UNAPI echo capability disabled
until payload, result and timeout semantics have been mapped and tested; the
existence of a PING command is insufficient.

The official [ioLibrary_Driver](https://github.com/Wiznet/ioLibrary_Driver/tree/e1791974e76d0b00cbac9e349ed92477b8d41386) includes
`Ethernet/W5100S`, socket support and `Internet/DNS` and `Internet/DHCP` clients.
It remains a candidate backend for the Pico study. The [software review](SOFTWARE-REVIEW.md)
pins and inspects these layers, including file-level licenses, blocking paths and
SPI callbacks. A host syntax check passes with warnings; platform timing, service
bounds and runtime behavior remain unqualified. No library code has been imported.

## Reading the vendor examples

Use the datasheet register descriptions and errata as the implementation baseline;
application-note pseudocode still needs review. In particular:

- The [TCP initialization example](https://docs.wiznet.io/Product/Chip/Ethernet/W5100S/Application-Note/tcp)
  loops with `n < 3`, omitting the fourth socket. Derive loop bounds from the
  selected allocation and verify every socket.
- The [UDP example](https://docs.wiznet.io/Product/Chip/Ethernet/W5100S/Application-Note/udp)
  comments on advancing over header plus payload, but its final increment shows
  only payload length. Its MTU-splitting statement also needs reconciliation with
  the product's fragmentation limitation. Do not infer fragmentation support.

The [roadmap](ROADMAP.md) tracks implementation and physical acceptance separately
from this documentation review.
